# MemFS 最佳实践指南

> MemFS 是知识卡片网络的数字孪生 MCP。本文档指导如何有效地组织和管理知识。
> GitHub: https://github.com/Qtgcy08/MemFS

---

## 零、核心工作流（每次遇新知必走）

用户引入新概念/术语/工具时，按以下顺序：

```
1. searchNode(query)           → 先查是否已有实体
2. 存在？→ addObservation       → 补充新信息
   不存在？→ createEntity        → 创建后再 addObservation
```

**反模式：** 不 search 直接 createEntity → 撞 Entity already exists 错误。

## 一、核心理念：知识卡片网络

### 1.1 什么是知识卡片

**知识卡片**是对一个独立概念的完整记录，包含：

| 字段 | 说明 | 要求 |
|-----|------|------|
| **name** | 概念的标准化名称 | 使用通用术语，不含冗余描述 |
| **entityType** | 偏正结构类型 | 见第二章 |
| **definition** | 启发性定义 | 见第三章 |
| **definitionSource** | 定义来源 | URL > 作品名 > 提出格式 |
| **observations** | 补充信息 | 独立知识点，不重复 definition |

### 1.2 知识卡片 vs 日常笔记

| 日常笔记 | 知识卡片 |
|---------|---------|
| 模糊判断 | 明确的关联关系 |
| 闲聊内容 | 不存储 |

**MemFS 只存储知识卡片，不存储闲聊内容。**

### 1.3 观察（Observation）的语义完整性原则

观察存储在独立的 inode 表中，可被多个实体共享。修改共享观察时系统自动 Copy-on-Write。

**核心规则：每条 observation 必须脱离父实体仍可独立理解。**（因为 searchNode 的 BM25 索引只命中 observation 内容本身，不附带 entity 上下文，且跨实体共享时父实体不唯一。）

**写法要求：**

| ❌ 禁止（破碎片段） | ✅ 正确（语义完整） |
|------------|-----------|
| "发表于 1922 年" | "涂尔干《宗教生活的基本形式》发表于 1912 年，是其晚年代表作" |
| "提出了'理想类型'" | "韦伯提出'理想类型'(Idealtypus)作为社会学方法论的核心工具" |
| "使用了 BM25 算法" | "MemFS 的 searchNode 使用 BM25+Fuse.js 混合检索，BM25 权重 0.7" |

**自检：** 遮住所属 entity name，还能完整理解吗？不能 → 重写。

## 二、实体类型

### 2.1 偏正结构体系

偏正结构 = `[修饰语]/[中心语]`，可嵌套多组修饰语。

**顶层分类**

| 类型 | 说明 |
|-----|------|
| `知识` | 认知性内容：人物、理论、概念、文献 |
| `图谱` | 关联性内容：事件、学派、时期、地域 |
| `工具` | 方法性内容：框架、方法、模型、技术 |

**二级分类**

| 知识/ | 图谱/ | 工具/ |
|-------|-------|-------|
| 人物 | 事件 | 框架 |
| 理论 | 学派 | 方法 |
| 概念 | 时期 | 模型 |
| 文献 | 地域 | 技术 |
| 命题 | | |

## 三、Definition 启发性原则

### 3.1 启发性定义

**启发性定义** = **本质揭示** + **关联线索**

模板：`{核心定义}，{关联概念/人物}，{代表性命题/作品}`

| 维度 | 说明 |
|-----|------|
| **本质揭示** | 说明概念的核心特征。若实体从上游项目衍生而来，需标注具体来源项目名（如「基于 server-memory 深度重构」），而非笼统写"基于 MCP" |
| **关联线索** | 指出相关的概念、人物、理论 |

写完 definition 后检查：
- [ ] 读后知道它**是什么**
- [ ] 读后知道**下一步查什么**
- [ ] 读后能**联想到相关概念**

## 五、关系（Relation）建立原则

### 5.1 关系类型（主动语态）

| 类型 | 适用场景 |
|-----|---------|
| `开创` | 理论/学派的创立 |
| `发展` | 后续推进 |
| `影响` | 思想启发 |
| `对立` | 理论反对 |
| `对比` | 并列比较 |
| `引用` | 文献引用 |
| `同时` | 同期学者 |
| `师生` | 教育指导 |
| `继承` | 学派传承 |
| `包含` | 整体与部分（如理论包含概念） |
| `属于` | 部分与整体（如概念归属于理论） |
| `应用` | 理论/技术被用于某场景 |
| `实现` | 工具/代码实现了某设计/协议 |
| `相关` | 模糊关联（最后选择，能精确就不用它） |

### 5.2 建立时机

**建立关系 when：**
- 发现明确的逻辑关联
- 读到明确的引用/影响/对立关系

**不建立关系 when：**
- 仅知道两者都存在
- 关联过于模糊

## 六、行为准则

**优先原则：尊重用户指令**

当用户指令与最佳实践建议冲突时，以用户指令为准。

**MemFS 只存储：**
- 可验证的事实
- 标准化的概念定义
- 明确的理论关联
- 有来源的论述
- 用户的思考与感想

**MemFS 不存储：**
- 模糊的"可能有关"
- 重复的已有信息

### 6.1 不主动滥存

Skill 触发不等于每条消息都要存。以下场景**不调用 MemFS 工具**：

- **一次性查询**："今天天气怎么样"——结果不需要持久化
- **纯闲聊**：个人偏好、当天情绪——由会话上下文处理
- **纯操作指令**："帮我打开浏览器""截图"——没有知识点
- **用户拒绝**："不用记""别存"——尊重用户

**该存时：** 用户引入新概念/术语/工具；明确说"记住""记录"；讨论中自然形成可复用知识点。

## 八、高级技巧：观察所有权转移

> 此用法是 `inode 表` 数据结构自然衍生的 Emergent Affordance，非设计时预设功能。

### 8.1 场景

研究过程中，一条观察（Observation）最初属于实体 A，但随着理论推演发现它更适合属于实体 B。传统方案需删除重建，MemFS 通过两步组合实现有序转移。

### 8.2 操作流程

```
Step 1: unlinkObservation(observationId, ["实体A"])
         → 解除观察与实体A的关联
         → 该观察进入「孤儿」状态

Step 2: addObservation({ mode: "link-single", entityName: "实体B", observationId: <id> })
         → 将同一观察链接到实体B
         → 观察 ID 不变，数据不复制
```

### 8.3 验证

转移完成后，可通过以下方式确认：

```
readNode("实体A")      → 确认原实体已不含该观察
readNode("实体B")      → 确认目标实体已关联该观察
getOrphanObservation() → 确认无残留孤儿观察
```

### 8.4 与传统方案对比

| 方案 | 操作 | 数据 |
|-----|------|------|
| 传统知识库 | 复制原文 → 删除原文 → 粘贴到新位置 | 数据被复制+删除，关联丢失 |
| MemFS 转移 | unlink → link | 数据原地不动，仅变更指针 |

### 8.5 进阶用法：观察跨实体复用

一条观察可同时链接到多个实体（共享 inode），无需复制内容：

```
// 创建时直接共享
createEntity([
  { name: "实体B", observations: ["同一内容"] },
  { name: "实体C", observations: ["同一内容"] }
])
// 底层：同一 observationId 被两个实体共享
```

## 十、观察去重清理流程

当用户要求整理某实体的观察、或 AI 自主发现同一实体下存在语义重复的观察时，执行以下标准流程：

### 10.1 三步工作流

```
Step 1: 批量读取 → readObservation 分批读取该实体所有观察内容
Step 2: 语义聚类 → 识别重复组，确定 keeper 并合并语义
Step 3: 三步清理 → updateObservation(合并) → unlinkObservation(解绑) → recycleObservation(回收)
```

### 10.2 识别重复的标准

两条观察应合并，如果满足以下任一条件：

- **同事件异录**：同一对话/事件被分多条记录，措辞略有差异
- **枚举拆散**：原本是 "1/2/3/4" 的枚举被拆成多条独立观察
- **后续合并版已覆盖**：存在一条后续记录的合并版观察，语义完全覆盖之前的分散记录
- **Keeper 已吸收**：合并后的 keeper 观察已包含被合并观察的全部信息

### 10.3 合并原则

- 挑选信息量最大、语义最完整的观察作为 keeper
- 用 `updateObservation` 将其他观察的独有信息融入 keeper
- 合并后 keeper 应自足可读，不依赖被删除的观察
- 合并完成后必须重新 `readNode` 验证

### 10.4 多轮清理意识

一次合并后可能仍有隐藏重复——因为合并后的 keeper 之间可能产生新的语义重叠。发现用户指出仍有重复时，应立即进行第二轮聚类分析，不要争辩。

### 10.5 清理完成后

主动告知用户：原始观察数 → 最终观察数、删除了多少条、合并了多少组。让用户确认是否需要 `readNode` 验证最终状态。

## 十一、常见重复模式

以下是实践中高频出现的重复模式，应在聚类分析时重点关注：

| 模式 | 特征 | 示例 |
|------|------|------|
| **枚举拆分** | 观察名带编号（1/2/3/4）且内容同主题 | "MCP优势1""MCP优势2"…→ 合并为一条 |
| **同话题多次记录** | 同一场 MCP/CLI/Skill 讨论在不同时间被多次写入 | 多条关于 "MCP 不会被 CLI 取代" 的观察 |
| **观点+情绪分离** | 理性分析和情绪反应被拆成两条 | "MCP已死论是营销概念" + "看到评论区有点上头" |
| **起源故事重叠** | 同一工具/理论的起源被多次从不同角度记录 | "基于server-memory修改" + "一开始觉得挺好" |
| **版本元数据散落** | npm 包名、仓库地址、关键词等分多条记录 | 应合并为一条完整的发布信息 |
