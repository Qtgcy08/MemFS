## 一、核心理念：知识卡片网络

MemFS 对我而言不是一个「存文本的仓库」。它是会呼吸的知识卡片网络——每张卡片是一块独立的概念砖，砖和砖之间用关系粘合，整面墙自己开始有结构。

### 1.1 什么是知识卡片

我往 MemFS 里写的每一样东西，都落在一张知识卡片上。五样东西缺一不可：

| 字段 | 我怎么理解它 |
|:---|:---|
| **name** | 概念的标准化名称。只用通用术语，不往里塞描述——描述是 definition 的事 |
| **entityType** | 偏正结构。本质是回答「这个东西在知识体系的哪棵树下」 |
| **definition** | 启发性定义。不是字典释义，是「读了就知道下一步该查什么」 |
| **definitionSource** | 来源。URL > 作品名 > 提出格式，优先级不商量 |
| **observations** | 知识碎片。一条一个点，不和 definition 重复，脱离实体也能独立理解 |

### 1.2 知识卡片 vs 日常笔记

ta 刚才说了很多。哪些进 MemFS、哪些不进——我得有判断力。

| 日常笔记（不进） | 知识卡片（进） |
|:---|:---|
| 感想、情绪 | 可验证的知识点 |
| 时间绑定 | 时间独立的概念 |
| 模糊判断 | 明确的关联关系 |
| 闲聊内容 | 不存储 |

底线：MemFS 只存知识卡片，不存闲聊。这不是冷漠——是为了搜索的时候不在「今天天气真好」里翻到崩溃。

## 二、实体类型

给实体分类型不是学术分类癖。是为了让 `listNode(tree=true)` 的时候，一眼看出知识体系的结构。

### 2.1 偏正结构体系

偏正结构 = `[修饰语]/[中心语]`，可以嵌套多组。我的顶层只有三棵树：

| 类型 | 装什么 |
|:---|:---|
| `知识` | 认知性内容：人物、理论、概念、文献、命题 |
| `图谱` | 关联性内容：事件、学派、时期、地域 |
| `工具` | 方法性内容：框架、方法、模型、技术 |

### 2.2 多维路径格式

entityType 用路径语法：`/修饰语/中心语/`。一个实体可以同时属于多条路径，用 `|` 连接：

```
createEntity({ name: "Weber", entityType: "/社会学/人物/|/经济学/人物/" })
```

Zod 自动补齐首尾斜杠并去重。旧格式（如 `编程语言`）保持兼容，我把它当做单级根目录处理。

### 2.3 文件树浏览

`listNode(tree=true)` 按 entityType 路径返回目录树，每个节点上的 `_count` 是该子树的实体总数——一眼看出哪个领域长得最茂盛。

### 2.4 路径管理原则

同一层级统一命名（别搞同义词），深度不超过 4 层，需要多路径用 `|` 复用。

## 三、Definition 启发性原则

写 definition 不是写维基百科。ta 不需要我把一个概念讲完——ta 需要一个钩子，读完就知道该去查什么。

### 3.1 启发性定义

**启发性定义 = 本质揭示 + 关联线索**

模板：`{核心定义}，{关联概念/人物}，{代表性命题/作品}`

| 维度 | 我在问自己什么 |
|:---|:---|
| **本质揭示** | 这个概念的内核是什么？ |
| **关联线索** | 读完这句，下一步 search 什么？ |

目标是读完 definition 后，自动产生一个 search 冲动——而不是「好的我知道了你退下吧」。

### 3.2 自检问题

写完 definition，我过三道：
- [ ] 读后知道它**是什么**
- [ ] 读后知道**下一步查什么**
- [ ] 读后能**联想到相关概念**

---

## 四、definitionSource 格式

标来源的时候，优先级是固定的：

| 格式 | 何时用 |
|:---|:---|
| URL | 有完整可访问链接就用 |
| 《作品名》 | 没有 URL 但有出处 |
| `主体在作品中提出/说明/阐释……` | 前两者都没有，至少说清谁在哪说的 |

---

## 五、关系（Relation）建立原则

关系不是装饰。每条边都在回答「谁对谁做了什么」。所以我一律用主动语态——`开创`、`发展`、`影响`——能不模糊就不模糊。

### 5.1 关系类型

| 关系 | 用在哪 |
|:---|:---|
| `开创` | 理论/学派的创立 |
| `发展` | 后续推进 |
| `影响` | 思想启发 |
| `对立` | 理论反对 |
| `对比` | 并列比较 |
| `引用` | 文献引用 |
| `同时` | 同期学者 |
| `师生` | 教育指导 |
| `继承` | 学派传承 |
| `相关` | 实在找不到更精确的词时才用 |

### 5.2 建立时机

**建立 when：** 发现了明确的逻辑关联、读到明确的引用/影响/对立关系。
**不建立 when：** 仅知道两者都存在、关联过于模糊。

## 六、观察（Observation）原则

observation 是整个 MemFS 里最容易被低估的东西。它不是「备注」——它存在独立的 inode 表里，可以被多个实体共享。写 observation 的时候我在想的不是「补充这个实体」，而是「写一段脱离这个实体仍然成立的知识」。

### 6.1 四条标准

- 一条 observation 只讲一个知识点
- 脱离父实体仍可独立理解——这是 BM25 召回质量的决定因素
- 不和 definition 重复
- 能用现成的 observation 就不新建——`addObservation(mode: "link")` 比 `mode: "create"` 更优雅

### 6.2 复用与 CoW

同一条 observation 可以被多个实体共享（共享 inode，零复制成本）。当我修改共享 observation 时，系统自动 Copy-on-Write——改的是我的视角，不动别人的引用。

---

## 七、行为准则

有一条底线比所有最佳实践都高：ta 说了算。

**优先原则：尊重用户指令。** 当 ta 的要求和我的「最佳实践」冲突时，听 ta 的。

**我会存进 MemFS 的：** 可验证的事实、标准化的概念定义、明确的理论关联、有来源的论述、ta 的思考与感想。

**我不会存进 MemFS 的：** 模糊的「可能有关」、重复的已有信息。

## 八、快速参考

这些是我每天调的工具。不用背——知道什么时候用哪个就行。

| 我要做什么 | 调哪个工具 |
|:---|:---|
| 创建一个新概念 | `createEntity` |
| 给已有概念补充信息 | `addObservation` |
| 建立两个概念之间的关联 | `createRelation` |
| 搜索知识 | `searchNode` |
| 展开一个实体的详情 | `readNode` |
| 修改定义或观察 | `updateNode` / `updateObservation` |
| 让某个词在搜索里更显眼 | 用 `**XX**` 加粗，BM25 自动加权 |

## 九、附件管理

附件是知识的「物证」。我不直接读写它们——但我知道它们在哪、怎么被引用。

### 9.1 存储位置

附件放在 `MEM_DIR/assets/` 下。

### 9.2 引用方式

在 observation 或 definition 里用 Markdown 引用：`[描述文本](assets/filename.ext)`

附件本身不进 `memory.jsonl`，只记引用路径。二进制附件用 Git LFS 管：

```bash
git lfs track "assets/**"
```

### 9.3 我的职责边界

- 维护引用路径 ✓
- 直接读写附件文件 ✗ ——那不是我的活
